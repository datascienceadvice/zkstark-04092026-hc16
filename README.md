# zkstark — ZK-протокол сравнения двух групп на Risc Zero

Проверяемое (zero-knowledge) сравнение двух независимых выборок на основе
Risc Zero zkVM: автоматический выбор критерия между **Уэлча t-тестом** и
**медианным тестом Муда** с точным p-уровнем Фишера 2×2, без раскрытия
сырых данных лабораторий.

Целевая задача-иллюстрация: концентрации аналита в крови двух лабораторий.
Лаборатории публикуют только **сводные статистики** (n, sum, sum²) и
доказывают корректность их вычисления; агрегатор верифицирует все
доказательства и публикует итог сравнения (t/df/p или M̂/a/b/p).

Ключевые свойства:

- **два раунда** протокола «лаборатория → агрегатор → лаборатория → агрегатор»,
  6 доказательств на одно сравнение (см. «Логика протокола»);
- **выбор критерия по данным**: нормальность каждой группы проверяется
  критерием Шапиро–Уилка (порт R `shapiro.test`), далее Уэлча t-тест либо
  медианный тест Муда;
- **приватность**: сырые значения не покидают гостей лаборатории; наружу идёт
  только агрегат (сводные, статистика Шапиро–Уилка, медиана группы,
  `count_above(M̂)` для теста Муда);
- **численный порт R**: спецфункции и распределения реализованы вручную
  (без внешних стат-крейтов) и совпадают с R 4.3.1 до ~1e-12;
- **воспроизводимость**: 20 фиксированных сценариев, golden-значения из R,
  журнал каждого receipt сверяется с ними в пределах допуска (по умолчанию 1e-9);
- **режимы**: `dev` (fake-receipts, честный journal — для быстрого CI) и
  `full` (настоящие STARK-доказательства).

> Рабочая копия разрабатывается в **Windows** (D:\lair\zkstark), но Risc Zero
> собирается только внутри **WSL2/Ubuntu** (у гостевого тулчейна нет Windows-сборки).
> См. «Сборка и запуск».

## Логика протокола

Протокол двухраундовый; каждая передача данных между сторонами оформлена
как отдельное ZK-доказательство (`env::read` → выполнение → `env::commit`).
Верификация встроена в композицию: на каждой стадии агрегатор **внутри
гостевой среды** проверяет оба лабораторных receipt через `env::verify`
(журналы лабораторий передаются агрегатору байтами и сравниваются горячо),
а итоговый receipt бенчмарк дополнительно верифицирует по `method_id`
извне. Итоговое доказательство агрегатора достоверно только если верны
все шесть лабораторных доказательств и их журналы совпадают с входом.

### Раунд 1 — подготовка

```
Lab1 (guest lab)              Lab2 (guest lab)
 RawSample x[]                 RawSample y[]
   ├─ summarize → (n1, s1, s²1)   ├─ summarize → (n2, s2, s²2)
   ├─ shapiro_wilk → (W1, p1)      ├─ shapiro_wilk → (W2, p2)
   └─ median → med1                └─ median → med2
        │                                │
        ▼                                ▼
   Aggregator (guest aggregator), раунд S1:
   both_normal = (sw1.p > α) && (sw2.p > α)
     · да  → Method::Welch,  M̂ = None
     · нет → Method::Mood,   M̂ = (med1 + med2)/2
   commit → Stage1Decision { method, alpha, m_hat }
```

Решение (и M̂ при Mood) публикует агрегатор; M̂ — единственная «секретная»
величина протокола, которая зависит от данных обеих групп.

### Раунд 2 — финализация

```
Lab1 (guest lab)              Lab2 (guest lab)
 повтор Round1-материализации  повтор Round1-материализации
 + count_above(M̂) → a          + count_above(M̂) → b
        │                                │
        ▼                                ▼
   Aggregator (guest aggregator), раунд S2:
   · Welch: welch_from_summary(stats1, stats2) → t/df/p  (t-CDF через
     регуляризованную неполную бета-функцию; двусторонний p напрямую, без
     вычитания 2·(1−CDF))
   · Mood:  fisher_two_sided_2x2(a, n1, b, n2) → точный двусторонний p
     (сумма вероятностей гипергеометрического распределения по таблицам
     не менее вероятным, чем наблюдаемая — как R fisher.test two.sided)
   commit → PipelineResult
```

Итог — `PipelineResult { method, alpha, sw1, sw2, welch?, median? }` в journal
агрегатора; для выбранного критерия заполнено ровно одно из `welch`/`median`.

### Что именно раскрывается

- Уэлч-путь: только (n, sum, sum²) каждой группы — эквивалентно mean/sd.
- Mood-путь: дополнительно медианы групп, M̂ и `count_above(M̂)` обеих групп
  (из этого агрегатор восстанавливает 2×2-таблицу и точный p). Суммарный
  ответ на M̂ — это осознанный компромисс: он необходим для таблицы 2×2.

### Формулы (кратко)

- mean = sum/n;  var = (sum² − sum²/n)/(n−1);  sd = √var.
- Welch: t = (mean₁−mean₂)/√(var₁/n₁ + var₂/n₂);  df по Саттертуэйту;
  p = I_{df/(df+t²)}(df/2, 1/2) (неполная бета).
- Shapiro–Wilk W и p — порт R (AS R94), применим для n ∈ [3, 5000].
- Mood: 2×2 с порогом строго «>»: `count_above(vals, M̂)`; p — точный Фишер.

## Сценарии и валидация против R

- `results/scenarios.csv` — сырые данные 20 сценариев (case → две группы);
- `results/scenario_meta.csv` — имена, α, n₁, n₂;
- `results/golden.csv` — эталон из R 4.3.1 (метрики: метод, sw1/2 w/p, медианы,
  welch t/df/p; для Mood — `mood.approx.*` по аппроксимации M̂ и `mood.exact.p`
  по истинной объединённой медиане);
- генератор: `scripts/golden.R` → `Rscript scripts/golden.R`;

Сценарии покрывают: нормальные разного размера/дисперсии, логнормальные,
гамма, экспоненциальные, равномерные, тяжёлые хвосты (t₃), бимодальные,
дискретные/пуассоновы, константную группу (ожидаемая ошибка Шапиро–Уилка),
крайне малые выборки (n=3) и крупные (n=1000).

Бенчмарк сверяет каждый метрику journal с golden в пределах допуска
(`--tol`, по умолчанию 1e-9). Наблюдаемые на всей матрице погрешности
≤ 2e-12.

## Сборка и запуск

Risc Zero собирается **только** внутри WSL2 (Linux): у risc0-тулчейна
нет Windows-варианта, а гостевой target — `riscv32im-risc0-zkvm-elf`.

Предпосылки (в WSL2/Ubuntu): Rust stable, `rzup` → `cargo-risczero` 2.3.2,
`r0vm` 2.3.2, тулчейн `risc0` 1.97.0 (ядро RISC-V). Если рабочие файлы
менялись на Windows — сначала синхронизировать:

```bash
wsl -e bash -lc "bash /mnt/d/lair/zkstark/scripts/sync_to_wsl.sh"
```

Далее все команды — внутри WSL (рабочий каталог `~/zkstark`):

```bash
# тесты спецификаций и протокола
cargo test -p zkstark-core

# быстрый прогон dev-режима (fake-receipts, честный journal)
cargo run -p bench --release --bin bench -- --mode dev --cases n01,n20

# полная матрица в dev (20 сценариев, ~10 c)
cargo run -p bench --release --bin bench -- --mode dev

# настоящие STARK-доказательства (медленно: 1–7 мин на малый сценарий)
cargo run -p bench --release --bin bench -- --mode full --cases n16,n02

# весь протокол на всех сценариях в full-режиме — НЕ запускать в одну команду:
# крупные/медианные сценарии дают минуты и риск нехватки памяти prover-сервера.

# экспорт результата прогона в CSV
target/release/bench --export-run <run_id>    # → results/report_<run_id>.csv
```

Параметры CLI bench:

| Флаг | Значение по умолчанию | Описание |
|---|---|---|
| `--mode` | `dev` | `dev` = fake-receipts (journal настоящий), `full` = реальные STARK-proof |
| `--cases` | `all` | подмножество сценариев, например `n01,n02` |
| `--tol` | `1e-9` | допуск относительной погрешности сверки с golden |
| `--db` | `results/zkstark.db` | путь к SQLite-БД |
| `--export` | — | после прогона писать `report_<run>.csv`/`errors_<run>.csv` |
| `--export-run` | — | экспорт существующего прогона по id |

### Сводные таблицы для статьи

```bash
# Windows:
& "D:\R\R-4.3.1\bin\Rscript.exe" analysis\make_tables.R     # CSV-таблицы + лог (UTF-8)
& "D:\R\R-4.3.1\bin\Rscript.exe" analysis\make_paper_tables.R  # table_paper_*.md для article
```

Скрипты читают `results/report_*.csv` и `results/golden.csv` и пишут

автоматический. Черновик статьи с встроенными таблицами — `analysis/paper.md`.

## Результаты (зафиксировано в results/)

- **dev-матрица (`results/report_16.csv`, свежие повторы в БД с тем же
  результатом)**: 20/20 сценариев, 19 `ok` +
  1 `expected_error` (константная группа, SW-ошибка намеренно); все проверки
  `pass`, max_rel_err ≈ 1.8e-12; ~86.6M циклов суммарно за ~9 c.
- **full-подмножество (`results/report_17.csv`, настоящие proof)**: n01, n02, n16 (Уэлча,
  включая n=3) — все `pass`: n01 ≈ 817 c (~13.6 мин, 1.44M циклов), n02 ≈
  515 c, n16 ≈ 368 c; композиция через `env::verify` работает и в боевом
  режиме. Медианный сценарий n06 в full упёрся в ограничение памяти
  prover-сервера (`prove: rx len failed` — падение r0vm-процесса на 11
  сегментах); корректность Mood подтверждена dev-матрицей.
- Циклы определённого гостевого образа воспроизводимы, но цифра меняется
  между пересборками (~±2%: 84.6M у ранних бинарей vs 86.6M у текущего)
  из-за недетерминированных метаданных гостевого ELF; image_id при этом
  стабилен, поэтому композиция и сверка с golden не зависят от этого.

## Ограничения и открытые вопросы

- «Точный» медианный тест использует M̂ = mean(median₁, median₂), а не
  истинную объединённую медиану — аппроксимация, от которой зависит выбор
  2×2-таблицы. Её погрешность сильно зависит от сценария: max |exact−approx|
  = 0.571 (n05, нормальные n=3/4) и остаётся заметной даже на умеренных n
  (n07, гамма 40/40: 0.562; n19, 25/25: 0.429; n02, 8/8: 0.305); при малых
  p-значениях/больших эффектах она исчезает (n06: ~7e-8; n18: ~6e-6).
  Вывод протокола при этом устойчив: **0 ложных значимостей** на 19 медианных
  сценариях (все 7 значимых по M̂ остаются значимыми по точной объединённой
  медиане); единственный разлёт — пограничный n01 (0.060 vs 0.031),
  закрываемый Уэлча-ветвью (SW: обе группы нормальны).
  Полный список — `analysis/tables/table_paper_mood.md`.
- Гости собираются **обязательно** на гостевое `std` risc0-zkvm
  (`default-features=false, features=["std"]`): для f64-математики
  (`sqrt`, `powf`, …) в `core` таргета `riscv32im-risc0-zkvm-elf`
  соответствующих интринсиков нет, строгий `#![no_std]`-гость без
  libm-замен невозможен; математика самого `core` при этом остаётся
  no_std-совместимой.
- Производтельность: полный proof для крупных сценариев (n=1000, ~25M
  циклов) занимает существенно больше времени; в CI использовать dev-режим.
